
# Bean Fundamentals in Spring Boot

---

# 1. First Understand What an Object Really Is

In Java:

```java
User user = new User();
```

What happens?

## Step-by-step

### Step 1

Memory gets allocated in Heap Memory.

Example:

```text
Heap Memory
-------------
User Object
name = null
age = 0
-------------
```

---

### Step 2

`user` variable stores the reference (address).

```text
user ---> Object Address
```

---

# 2. What Does "Creating an Object" Mean?

Object creation means:

- allocating memory
- initializing fields
- calling constructor
- storing object reference

Example:

```java
User user = new User();
```

creates NEW memory every time.

---

# 3. Without Spring

Imagine:

```java
EmailService emailService = new EmailService();
OrderService orderService =
    new OrderService(emailService);
```

YOU manually create everything.

In small apps this is okay.

In large apps:

- thousands of objects
- dependency chains
- object lifecycle problems
- configuration problems

becomes difficult.

---

# 4. What Problem Does Spring Solve?

Spring says:

> "I will create and manage objects for you."

This is called:

# Inversion of Control (IoC)

Meaning:

Instead of YOU controlling object creation,
Spring controls it.

---

# 5. What is Dependency Injection?

Example:

```java
@Component
public class EmailService {
}
```

```java
@Component
public class OrderService {

    private final EmailService emailService;

    public OrderService(
        EmailService emailService
    ) {
        this.emailService = emailService;
    }
}
```

Spring sees:

```text
OrderService needs EmailService
```

So Spring automatically injects it.

This is:

# Dependency Injection (DI)

---

# 6. Why Is Dependency Injection Useful?

Without DI:

```java
public class OrderService {

    private EmailService emailService =
        new EmailService();
}
```

Problems:

- tightly coupled
- hard to test
- difficult to replace
- bad maintainability

---

With DI:

```java
public class OrderService {

    private final EmailService emailService;

    public OrderService(
        EmailService emailService
    ) {
        this.emailService = emailService;
    }
}
```

Advantages:

- loose coupling
- easy testing
- flexible architecture
- replace implementations easily

---

# 7. What Is ApplicationContext?

Think of it as:

# Spring's Object Container

It stores all beans.

Example:

```text
ApplicationContext
--------------------
emailService
orderService
userService
paymentService
--------------------
```

Spring creates objects and stores them here.

---

# 8. What Is Dependency Lookup?

Dependency Injection:

Spring gives objects automatically.

Dependency Lookup:

YOU ask Spring for objects manually.

Example:

```java
ApplicationContext context =
    new AnnotationConfigApplicationContext(AppConfig.class);

EmailService emailService =
    context.getBean(EmailService.class);
```

This is:

# Dependency Lookup

---

# 9. DI vs Dependency Lookup

| Feature | DI | Dependency Lookup |
|---|---|---|
| Who gets object? | Spring injects | You request |
| Cleaner? | Yes | Less |
| Modern style? | Yes | Rarely used |
| Recommended? | Yes | Mostly no |

---

# 10. Why Is `getBean()` Rarely Used?

Because it creates:

- tight coupling with Spring
- difficult testing
- ugly code

Modern Spring prefers constructor injection.

---

# 11. What Is a Bean Scope?

Scope means:

# "How many objects should Spring create?"

---

# 12. Singleton Scope (Default)

Default scope:

```java
@Component
public class EmailService {
}
```

Spring creates ONLY ONE object.

Example:

```text
Application Start
    ↓
Create ONE EmailService object
    ↓
Reuse everywhere
```

---

# 13. Real Memory View of Singleton

```text
Heap Memory
--------------------------------
EmailService Object
--------------------------------

UserController ----┐
OrderService ------┼----> same object
PaymentService ----┘
```

Everyone shares same object.

---

# 14. Why Singleton Is Default?

Because most services are:

- stateless
- reusable
- lightweight

Creating objects repeatedly wastes memory.

Singleton improves:

- performance
- startup speed
- memory usage

---

# 15. Prototype Scope

```java
@Component
@Scope("prototype")
public class EmailService {
}
```

Now:

Spring creates NEW object every request.

Example:

```text
Request 1 -> Object A
Request 2 -> Object B
Request 3 -> Object C
```

---

# 16. Real Memory View of Prototype

```text
Heap Memory

EmailService A
EmailService B
EmailService C
```

Multiple objects exist.

---

# 17. Your Important Question:
# "Will User Data Overwrite in Singleton?"

NO.

This is a VERY common beginner confusion.

---

# 18. Example Understanding

Suppose:

```java
@Service
public class UserService {

    public void createUser(User user) {
        repository.save(user);
    }
}
```

`UserService` is singleton.

BUT:

```java
User user
```

inside request is DIFFERENT every time.

---

# 19. What Actually Changes Per Request?

When client sends POST request:

```json
{
  "name": "Jhon"
}
```

Spring creates NEW request objects:

```text
Request 1:
User Object A

Request 2:
User Object B
```

These are NOT singleton beans.

They are temporary request data objects.

---

# 20. Important Difference

## Singleton Bean

```java
@Service
public class UserService {
}
```

Created ONCE.

Shared.

---

## Request Data Object

```java
User user
```

Created per request.

Destroyed later by Garbage Collector.

---

# 21. Then Why Do We Avoid Mutable State?

BAD:

```java
@Service
public class UserService {

    private User currentUser;
}
```

Why dangerous?

Because ALL users share same singleton object.

Example:

```text
User A request changes currentUser
User B request changes currentUser
```

Data corruption possible.

---

# 22. Good Singleton Design

Singleton services should be:

# Stateless

GOOD:

```java
@Service
public class UserService {

    public void createUser(User user) {
        repository.save(user);
    }
}
```

No shared mutable fields.

---

# 23. Garbage Collector Question

Yes.

Request objects usually become unreachable after request completes.

Then:

# Garbage Collector frees memory.

Example:

```text
Request Finished
    ↓
Object no longer referenced
    ↓
GC removes it later
```

---

# 24. Then Why Use Singleton Beans?

Because services contain:

- logic
- configuration
- reusable behavior

NOT request-specific user data.

Example:

```java
EmailService
PaymentService
JwtService
UserService
```

These don't need recreation every request.

---

# 25. Real World Analogy

## Singleton

Restaurant Kitchen.

One shared kitchen serves everyone.

---

## Prototype

Disposable paper cup.

Create new one each time.

---

# 26. When Should You Use Prototype?

Rarely.

Useful when object contains:

- temporary state
- request-specific workflow
- mutable processing data

Examples:

- report builders
- parsers
- workflow processors

Most services remain singleton.

---

# 27. What Is `@ComponentScan`?

YES.
It exists.

Example:

```java
@ComponentScan("com.example")
```

It tells Spring:

# "Scan this package for components."

---

# 28. Then Why Don't We Use It Often in Spring Boot?

Because:

```java
@SpringBootApplication
```

already includes:

```java
@ComponentScan
```

internally.

---

# 29. Internally `@SpringBootApplication` Is:

```java
@Configuration
@EnableAutoConfiguration
@ComponentScan
```

combined together.

---

# 30. When Do We Use `@ComponentScan` Explicitly?

When beans exist outside default package structure.

Example:

```text
com.app.main
com.external.services
```

Need:

```java
@ComponentScan({
    "com.app.main",
    "com.external.services"
})
```

Beans exist because:

# Object creation and dependency management become difficult in large systems.

Spring centralizes:

- object creation
- lifecycle management
- dependency wiring
- configuration
- reuse

# 34. Most Important Beginner Understanding

Services are usually singleton because:

They contain BEHAVIOR,
not USER DATA.

Request/user data is usually:
- temporary
- request scoped
- method-local
- garbage collected later

This is why singleton services are safe
when designed properly.
